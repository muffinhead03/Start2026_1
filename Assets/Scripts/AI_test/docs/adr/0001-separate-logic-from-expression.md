# 0001. 힌트 판단(로직)과 표현(AI)을 분리한다

## Context

방탈출 게임의 힌트 시스템을 만들 때 두 가지 극단이 있다.

1. **고정 텍스트 힌트**: 미리 작성된 문구를 그대로 노출. 모든 플레이어에게 동일하게 작동하지만, 상황(플레이어가 얼마나 막혔는지)을 반영하지 못해 너무 이르면 스포일러, 너무 늦으면 무의미하다.
2. **LLM에 판단까지 위임**: "플레이어가 막혔으니 힌트를 줘"라는 지시만 LLM에 전달하고, 언제·얼마나 알려줄지도 LLM이 알아서 정하게 함. 유연하지만 할루시네이션으로 스포일러가 새거나, 아예 틀린 방향을 안내할 위험이 있고, 재현 불가능(같은 상황에서 다른 판단)하다는 문제도 있다.

## Decision

**"언제, 얼마나 많은 정보를 줄지"는 결정론적 코드(`HintEngine`)가 판단하고, LLM(`PromptBuilder` + LLM 클라이언트)은 그 판단 결과를 자연어로 표현하는 역할만 담당한다.**

`HintEngine.Calculate()`는 플레이어 상태(`PlayerState`)와 퍼즐 설정(`PuzzleConfig`)만으로 힌트 레벨(1~5)과 다음 안내 스텝을 순수 함수로 계산한다. LLM에는 이미 결정된 레벨에 해당하는 정보만 프롬프트로 전달되며, 그보다 상위 레벨의 정보(아직 공개되면 안 되는 정답)는 애초에 프롬프트에 포함되지 않는다.

## Consequences

**장점**
- 재현 가능(같은 `PlayerState`+`PuzzleConfig`면 항상 같은 레벨 판단)
- 스포일러 유출을 LLM의 지시사항 준수 여부에 의존하지 않고 구조적으로 차단(애초에 정보를 안 줌)
- 힌트 판단 로직만 따로 유닛 테스트 가능
- LLM 백엔드를 바꿔도(Ollama → LLMUnity 등) 판단 로직은 전혀 영향받지 않음

**트레이드오프**
- 힌트 레벨 기준(가중치, 임계값)을 세밀하게 튜닝하는 별도 작업이 필요함 — LLM에게 "알아서 판단해"라고 맡기는 것보다 초기 설계 비용이 더 든다
- 새로운 판단 요소를 추가하려면 코드 수정이 필요함(LLM 프롬프트만 바꿔서 될 일이 아님)
